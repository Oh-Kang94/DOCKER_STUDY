# 11. Stack 파일과 환경 분리

## Swarm Stack 형식

`docker stack deploy`는 최신 Docker Compose의 모든 기능이 아니라 Swarm 배포가 지원하는 Legacy Compose v3 계열 형식을 사용한다. `build` 대신 Registry에 Push된 `image`를 지정한다.

```yaml
version: "3.8"
services:
  api:
    image: registry.infra.local/apps/api@sha256:<digest>
    networks: [backend]
    deploy:
      replicas: 3
      update_config:
        parallelism: 1
        delay: 10s
        order: start-first
      rollback_config:
        parallelism: 1
      placement:
        constraints:
          - node.labels.zone == rack-a

networks:
  backend:
    driver: overlay
```

## 환경 분리

```text
stacks/platform.yml.j2       공통 구조
inventories/dev/group_vars/  개발 값
inventories/prod/group_vars/ 운영 값
vault/                       암호화된 민감 입력
```

Jinja는 Image Digest, Replica, Constraint와 외부 Config 이름처럼 환경별로 달라지는 값에 제한한다. Template 조건문이 지나치게 많아지면 결과를 Review하기 어렵다.

```yaml
image: "{{ api_image_repository }}@{{ api_image_digest }}"
deploy:
  replicas: {{ api_replicas }}
```

## Volume과 Data

Named Volume은 기본적으로 Task가 실행된 Node의 Local Docker Volume이다. Service가 다른 Node로 이동해도 같은 Data가 자동 연결되지 않는다. NFS Plugin, CSI 대체 도구 또는 Application Replication의 장애 특성을 별도로 검증한다.

## 사전 Render

```bash
docker stack config -c rendered/platform.yml
```

이 명령은 Stack 형식과 최종 병합 결과를 확인하지만 Image Pull, Secret 존재, Placement 가능성과 Application Readiness까지 검증하지 않는다.

## 현재 운영 기준

- Image는 Build하지 않고 검증된 Registry Artifact를 참조한다.
- Secret 값은 Stack 파일에 직접 Render하지 않는다.
- 외부 Network·Config·Secret의 생성 책임을 명확히 한다.
- Rendered Stack을 배포 Artifact로 보존하되 민감정보 포함 여부를 검사한다.
