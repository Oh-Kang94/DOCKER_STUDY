# 7. Node Label과 Scheduling 준비

## Label의 역할

Swarm Scheduler는 Node Label과 Placement Constraint를 비교해 Task를 배치한다. 온프레미스의 Rack, GPU, Local Storage 같은 차이를 Inventory에서 선언한다.

```yaml
swarm_labels:
  zone: rack-a
  storage: ssd
  gpu: "false"
```

```yaml
- name: Node Label을 Inventory와 맞춘다
  community.docker.docker_node:
    hostname: "{{ inventory_hostname }}"
    labels: "{{ swarm_labels }}"
    labels_state: replace
  delegate_to: "{{ groups['swarm_managers'][0] }}"
```

`replace`는 수동 Label을 제거할 수 있으므로 Inventory를 유일한 원본으로 삼을 때만 사용한다. 그렇지 않으면 추가·삭제 정책을 분리한다.

## Placement Constraint

```yaml
services:
  database:
    image: registry.infra.local/db@sha256:<digest>
    deploy:
      placement:
        constraints:
          - node.labels.storage == ssd
          - node.labels.zone == rack-a
```

조건을 만족하는 Ready Node가 없으면 Task는 `Pending`에 머문다. Constraint를 늘릴수록 장애 시 대체 Node가 줄어든다.

## Availability

| 값 | 의미 |
|---|---|
| `active` | 새 Task를 받을 수 있음 |
| `pause` | 기존 Task는 유지하고 새 Task를 받지 않음 |
| `drain` | 기존 Task를 다른 Node로 이동하고 새 Task를 받지 않음 |

Manager에서 Application Task를 실행하지 않으려면 Manager Node를 `drain`으로 둘 수 있다. Manager가 3대뿐인 소규모 환경에서는 별도 Worker Capacity가 충분한지 먼저 확인한다.

## Local Storage 주의

`storage=ssd` Label만으로 Data가 다른 SSD Node에 복제되지는 않는다. Local Volume을 사용하는 Stateful Service는 Task 이동 시 Data 접근이 끊길 수 있다. 공유 Storage, Replicated Storage 또는 Application 자체 복제를 별도로 설계한다.

## 현재 운영 기준

- Label Key와 허용값을 문서화한다.
- Hostname이 아니라 장애 Domain과 Capability를 표현한다.
- Constraint 변경 전 만족 가능한 Node 수를 계산한다.
- Maintenance는 먼저 Drain하고 Task 수렴을 확인한 뒤 진행한다.
