# 12. Dependency와 Library Chart

## Dependency 선언

```yaml
apiVersion: v2
name: platform
version: 1.3.0
dependencies:
  - name: redis
    version: 22.0.1
    repository: https://charts.example.com
    condition: redis.enabled
  - name: common
    version: 2.4.0
    repository: oci://registry.example.com/charts
```

`Chart.yaml`은 원하는 Dependency를 선언하고 `Chart.lock`은 해석된 Version과 Digest를 고정한다.

```bash
helm dependency update ./platform
helm dependency build ./platform
```

- `update`는 Version 조건을 다시 해석해 Lock 파일을 갱신한다.
- `build`는 기존 Lock 파일을 기준으로 `charts/`를 복원한다.
- CI와 재현 배포에서는 검토된 Lock 파일을 기준으로 `build`한다.

## Subchart Values

```yaml
redis:
  enabled: true
  architecture: standalone

global:
  imageRegistry: registry.infra.local
```

Parent Chart는 Subchart 이름 아래에서 값을 전달한다. `global`은 여러 Chart가 공유할 수 있지만 이름 충돌과 암묵적 결합이 생기므로 Registry·Domain 같은 명확한 공통값에 제한한다.

`condition`과 `tags`는 선택적 Component를 켜고 끈다. Production에서 필요한 DB까지 단순 Boolean 하나로 생성·삭제되도록 만들기보다 외부 DB 사용 여부와 Data Lifecycle을 분리한다.

## Library Chart

Library Chart는 배포 Resource를 직접 만들지 않고 공통 Named Template을 제공한다.

```yaml
apiVersion: v2
name: company-common
type: library
version: 1.0.0
```

Label, Pod SecurityContext와 Probe Template을 재사용할 수 있지만 너무 큰 공통 Template은 각 Application의 요구를 숨긴다. 입력 계약과 Version 정책을 일반 Library처럼 관리한다.

## Helm 4 Content Cache

Helm 4의 Content 기반 Cache는 같은 Dependency Content의 중복 저장을 줄이는 방향으로 동작한다. 사용자는 여전히 `Chart.lock`, Registry의 불변 Artifact와 Digest를 재현성 기준으로 삼아야 한다. Local Cache 자체를 배포 원본으로 취급하지 않는다.

## 현재 운영 기준

- Dependency Version 범위를 과도하게 넓히지 않는다.
- Lock 파일 변경은 Chart 변경과 함께 Review한다.
- Subchart의 CRD·Hook·Secret 생성 여부를 설치 전에 확인한다.
- 외부 Chart를 그대로 신뢰하지 않고 Render 결과와 권한을 검토한다.
