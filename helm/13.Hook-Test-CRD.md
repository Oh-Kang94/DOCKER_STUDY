# 13. Hook·Test·CRD

## Hook Lifecycle

Hook은 일반 Resource 배포 전후에 실행할 작업을 정의한다.

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: {{ include "api.fullname" . }}-migrate
  annotations:
    helm.sh/hook: pre-upgrade
    helm.sh/hook-weight: "-10"
    helm.sh/hook-delete-policy: before-hook-creation,hook-succeeded
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migrate
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
          args: ["migrate"]
```

Weight가 작은 Hook부터 실행된다. Migration Job은 재실행되어도 안전해야 하며 실패 후 수동 복구 기준도 있어야 한다. Hook Resource는 Release의 일반 Resource와 같은 방식으로 수명주기가 관리되지 않으므로 Delete Policy를 명시한다.

## Helm Test

`helm.sh/hook: test`가 붙은 Pod나 Job으로 설치된 Release를 점검한다.

```yaml
metadata:
  annotations:
    helm.sh/hook: test
    helm.sh/hook-delete-policy: before-hook-creation,hook-succeeded
```

```bash
helm test api -n apps --logs
```

Test는 Cluster 내부 Service 연결과 기본 응답을 확인하기 좋다. 외부 사용자의 전체 경로, 장시간 부하와 Data 정합성 검증을 모두 대신하지는 않는다.

## CRD 배치 방식

| 방식 | 특징 |
|---|---|
| `crds/` | Template 전에 설치, Upgrade·삭제를 Helm이 일반 Resource처럼 관리하지 않음 |
| `templates/` | 일반 Render 대상이지만 CRD와 CR의 설치 순서·Discovery 문제를 직접 해결해야 함 |
| 별도 CRD Chart | CRD Lifecycle과 Application Release를 분리 가능 |

CRD가 제공된 직후 Custom Resource를 설치해야 하면 API Discovery와 Controller 준비 시점을 고려한다. 운영에서는 CRD Owner와 Upgrade 절차를 Application Chart와 별도로 명확히 두는 편이 안전하다.

## 현재 운영 기준

- Hook에 장기 실행 Service를 두지 않는다.
- Migration은 이전·새 Application Version 모두와 호환되는 순서를 설계한다.
- Test 실패를 배포 실패로 처리할지 Pipeline 정책으로 명시한다.
- CRD 삭제를 일반 Uninstall 정리 작업에 포함하지 않는다.
