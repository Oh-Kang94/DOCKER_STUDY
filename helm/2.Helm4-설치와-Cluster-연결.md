# 2. Helm 4 설치와 Cluster 연결

## Helm 4 설치와 Version 확인

macOS에서는 Package Manager로 설치할 수 있다.

```bash
brew install helm
helm version
helm env
```

예상 결과의 Major Version이 `v4`인지 확인한다. Production에서는 `latest`를 막연히 따라가기보다 개발·CI·운영에 같은 검증된 Minor·Patch Version을 배포한다.

## kubeconfig와 Context

Helm은 kubectl과 같은 kubeconfig를 사용한다.

```bash
kubectl config current-context
kubectl config get-contexts
helm list --all-namespaces
```

명시적으로 Context와 Namespace를 지정하면 잘못된 Cluster 배포를 줄일 수 있다.

```bash
helm list --kube-context onprem-prod -n apps
helm install api ./api-chart \
  --kube-context onprem-prod \
  --namespace apps \
  --create-namespace
```

`--create-namespace`는 Namespace만 만들 뿐 ResourceQuota, NetworkPolicy와 RBAC 정책까지 만들어주지 않는다.

## Kubernetes Version Compatibility

Helm Client는 특정 Kubernetes Client Library로 빌드된다. 사용 중인 Helm Release가 대상 Kubernetes Version을 지원하는지 공식 Version Support Policy와 Release Note로 확인한다.

Chart도 `Chart.yaml`의 `kubeVersion`으로 지원 범위를 표현할 수 있다.

```yaml
apiVersion: v2
name: api
version: 0.1.0
kubeVersion: ">=1.33.0-0 <1.37.0-0"
```

이 제약은 호환성 표시와 설치 차단에 도움을 주지만 실제 CRD·Admission·CNI 호환성까지 보장하지는 않는다.

## RBAC 사전 점검

Helm은 실행 Identity가 가진 권한만 사용할 수 있다.

```bash
kubectl auth can-i create deployments -n apps
kubectl auth can-i create secrets -n apps
kubectl auth can-i create clusterroles
```

ClusterRole·CRD처럼 Cluster-scoped Resource가 포함된 Chart는 Namespace 배포 권한만으로 설치할 수 없다. 무조건 `cluster-admin`을 주기보다 Render 결과에서 필요한 Resource와 Verb를 식별한다.

## 배포 전 확인 순서

1. `helm version`과 Kubernetes Context를 확인한다.
2. Namespace와 RBAC 범위를 확인한다.
3. Chart·Values Version을 고정한다.
4. `helm lint`와 `helm template`로 정적 검토한다.
5. Non-production Cluster에서 먼저 적용한다.
