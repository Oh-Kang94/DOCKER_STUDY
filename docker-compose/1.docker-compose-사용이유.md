# 1. Docker Compose를 사용하는 이유

## Docker Compose란?

Docker Compose는 여러 컨테이너로 구성된 애플리케이션을 하나의 YAML 파일로 정의하고 관리하는 도구이다.

웹 애플리케이션은 보통 하나의 컨테이너만으로 끝나지 않는다. 웹 서버, 애플리케이션, 데이터베이스, 캐시처럼 역할이 다른 여러 컨테이너가 함께 동작한다. 각 컨테이너를 `docker run`으로 하나씩 실행할 수도 있지만, 컨테이너가 많아질수록 옵션과 실행 순서를 관리하기 어려워진다.

Compose 파일에는 다음 내용을 선언할 수 있다.

- 어떤 이미지를 사용할지
- 이미지를 직접 빌드할지
- 컨테이너에 어떤 환경 변수와 명령을 전달할지
- 호스트와 컨테이너의 포트를 어떻게 연결할지
- 서비스가 어떤 네트워크와 볼륨을 사용할지
- 서비스 사이에 어떤 시작 조건이 있는지

Compose는 Dockerfile을 대신하지 않는다. Dockerfile이 **컨테이너 이미지 하나를 만드는 방법**을 정의한다면, Compose 파일은 **여러 컨테이너를 어떤 구성으로 실행할지**를 정의한다.

## `docker run`만 사용할 때의 불편함

애플리케이션과 PostgreSQL을 직접 실행한다고 가정하면 네트워크와 볼륨을 먼저 만들고, 각 컨테이너에 긴 옵션을 전달해야 한다.

```bash
docker network create sample-network
docker volume create postgres-data

docker run -d \
  --name db \
  --network sample-network \
  -e POSTGRES_USER=study \
  -e POSTGRES_PASSWORD=secret \
  -e POSTGRES_DB=app \
  -v postgres-data:/var/lib/postgresql/data \
  postgres:18-alpine

docker run -d \
  --name web \
  --network sample-network \
  -e DB_HOST=db \
  -p 8080:8080 \
  example/web:1.0
```

이 방식에는 다음 문제가 있다.

- 실행 옵션이 셸 기록이나 별도 문서에 흩어지기 쉽다.
- 컨테이너 생성 순서와 정리 순서를 직접 관리해야 한다.
- 다른 사람이 동일한 환경을 재현하기 어렵다.
- 옵션 하나를 변경했을 때 어떤 컨테이너를 다시 만들어야 하는지 판단해야 한다.
- 프로젝트가 여러 개면 같은 이름의 컨테이너, 네트워크, 볼륨이 충돌할 수 있다.

Compose를 사용하면 같은 구성을 `compose.yaml`에 기록할 수 있다.

```yaml
name: sample-app

services:
  db:
    image: postgres:18-alpine
    environment:
      POSTGRES_USER: study
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: app
    volumes:
      - postgres-data:/var/lib/postgresql/data

  web:
    image: example/web:1.0
    environment:
      DB_HOST: db
    ports:
      - "8080:8080"
    depends_on:
      - db

volumes:
  postgres-data:
```

```bash
docker compose up -d
```

한 명령으로 선언된 서비스, 기본 네트워크와 볼륨을 준비하고 컨테이너를 실행할 수 있다.

## Docker Compose의 장점

### 1. 실행 구성을 코드로 관리

긴 `docker run` 명령 대신 YAML 파일에 구성을 남긴다. Compose 파일을 Git으로 관리하면 누가 어떤 옵션을 바꿨는지 확인하고 이전 구성과 비교할 수 있다.

### 2. 동일한 환경 재현

Compose 파일과 필요한 환경 변수만 공유하면 개발자와 CI 환경에서 비슷한 구성을 만들 수 있다. 다만 `latest`처럼 변경 가능한 이미지 태그, 호스트별 경로와 CPU 아키텍처 차이까지 Compose가 없애 주는 것은 아니다.

### 3. 여러 서비스의 생명주기 관리

`up`, `stop`, `start`, `down` 같은 명령으로 프로젝트에 속한 여러 컨테이너를 함께 관리할 수 있다.

### 4. 기본 네트워크와 서비스 이름 기반 통신

Compose는 프로젝트마다 기본 네트워크를 만든다. 같은 네트워크의 컨테이너는 IP 주소가 아니라 서비스 이름으로 서로를 찾을 수 있다.

```text
web 컨테이너 → db:5432 → db 컨테이너
```

컨테이너가 재생성되어 IP가 바뀌어도 `db`라는 서비스 이름은 유지된다. 컨테이너 내부에서 다른 서비스를 호출할 때 `localhost`를 사용하면 자기 자신을 가리키므로 주의해야 한다.

### 5. 프로젝트 단위 격리

Compose는 서비스, 네트워크와 볼륨을 프로젝트 단위로 묶는다. 기본 프로젝트 이름은 Compose 파일이 있는 디렉터리 이름에서 결정되며 `name`, `-p` 또는 `COMPOSE_PROJECT_NAME`으로 변경할 수 있다.

## 언제 사용하면 좋은가?

Docker Compose는 다음 상황에 잘 맞는다.

- 로컬 개발 환경에서 애플리케이션과 DB를 함께 실행할 때
- 테스트나 CI에서 동일한 의존 서비스를 준비할 때
- 한 호스트에서 소규모 다중 컨테이너 애플리케이션을 관리할 때
- 예제와 개발 환경을 문서화해 다른 사람과 공유할 때

Compose 자체는 여러 호스트에 컨테이너를 분산 배치하고 장애 시 다른 노드로 옮기는 오케스트레이터가 아니다. 멀티 노드 스케줄링과 클러스터 관리는 Swarm이나 Kubernetes 같은 별도의 오케스트레이션 영역이다.

## 현재 Compose에서 기억할 점

- 현재 CLI는 하이픈이 없는 `docker compose` 형식을 사용한다. `docker-compose`는 Compose V1에서 사용하던 형식이다.
- 기본 파일 이름으로 `compose.yaml` 또는 `compose.yml`을 사용할 수 있다. 이전 이름인 `docker-compose.yaml`도 지원된다.
- 최신 Compose Specification에서는 최상위 `version` 항목이 더 이상 파일 형식을 선택하지 않으며 obsolete 상태이다. 새 파일에서는 생략한다.
