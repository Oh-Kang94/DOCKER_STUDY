# 3. Docker Compose 작성 방법

## Compose 파일의 기본 구조

Compose 파일은 YAML 형식으로 작성하며 기본 파일 이름은 `compose.yaml`이다.

```yaml
name: compose-study

services:
  web:
    image: adminer:4

  db:
    image: postgres:18-alpine

networks:
  default:

volumes:
  db-data:
```

주요 최상위 항목은 다음과 같다.

| 항목 | 역할 |
| --- | --- |
| `name` | Compose 프로젝트 이름 지정 |
| `services` | 실행할 서비스와 컨테이너 설정 정의 |
| `networks` | 서비스가 사용할 네트워크 정의 |
| `volumes` | 영구 데이터를 저장할 named volume 정의 |
| `configs` | 컨테이너에 파일 형태로 전달할 일반 설정 정의 |
| `secrets` | 서비스에 명시적으로 허용할 민감한 데이터 정의 |

최신 Compose Specification에서는 최상위 `version`이 파일 형식을 선택하지 않는다. 하위 호환을 위해 남아 있지만 obsolete 상태이므로 새 파일에서는 작성하지 않는다.

YAML은 들여쓰기로 계층을 표현한다. 탭 대신 공백을 사용하고, 같은 단계의 항목은 들여쓰기 깊이를 맞춘다.

## 전체 예시

다음은 PostgreSQL과 데이터베이스 관리 도구인 Adminer를 함께 정의한 예시이다.

```yaml
name: compose-study

services:
  db:
    image: postgres:18-alpine
    environment:
      POSTGRES_USER: study
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?POSTGRES_PASSWORD is required}
      POSTGRES_DB: app
    volumes:
      - db-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER} -d $${POSTGRES_DB}"]
      interval: 10s
      timeout: 5s
      retries: 5
    networks:
      - backend

  adminer:
    image: adminer:4
    environment:
      ADMINER_DEFAULT_SERVER: db
    ports:
      - "127.0.0.1:8080:8080"
    depends_on:
      db:
        condition: service_healthy
    networks:
      - backend

networks:
  backend:
    driver: bridge

volumes:
  db-data:
    driver: local
```

이 예시에서:

- 프로젝트 이름은 `compose-study`이다.
- `db`와 `adminer`라는 두 서비스가 존재한다.
- 두 서비스는 `backend` 네트워크에서 서비스 이름으로 통신한다.
- Adminer는 `db`라는 호스트 이름으로 PostgreSQL에 접근한다.
- PostgreSQL의 데이터는 `db-data`에 저장되어 컨테이너 재생성 후에도 유지된다.
- Adminer의 호스트 포트는 `127.0.0.1`에만 바인딩되어 외부 인터페이스에 노출되지 않는다.
- `${POSTGRES_PASSWORD:?...}`는 값이 없으면 Compose가 오류를 내도록 하는 변수 치환 문법이다.
- healthcheck의 `$$`는 Compose가 아니라 컨테이너 내부 셸에서 `$POSTGRES_USER`를 해석하도록 `$`를 이스케이프한다.

## 서비스 정의

`services` 아래의 각 키가 서비스 이름이 된다.

```yaml
services:
  web:
    image: nginx:alpine
```

### `image`

컨테이너가 사용할 이미지와 태그를 지정한다.

```yaml
services:
  web:
    image: nginx:alpine
```

태그를 생략하면 기본적으로 `latest`가 사용된다. `latest`는 같은 이름으로 내용이 바뀔 수 있으므로 재현성이 중요한 환경에서는 명시적인 버전 태그나 digest 사용을 고려한다.

### `build`

Dockerfile을 이용해 이미지를 빌드할 방법을 지정한다.

간단한 형식에서는 빌드 컨텍스트 경로만 작성한다.

```yaml
services:
  api:
    build: ./api
```

상세 형식에서는 Dockerfile, 빌드 인자와 멀티 스테이지 target 등을 지정할 수 있다.

```yaml
services:
  api:
    build:
      context: ./api
      dockerfile: Dockerfile.dev
      target: development
      args:
        GO_VERSION: "1.25"
    image: example/api:dev
```

상대 경로는 Compose 파일의 프로젝트 디렉터리를 기준으로 해석된다. `image`도 함께 지정하면 빌드한 결과에 해당 이름과 태그를 사용할 수 있다.

### `environment`

컨테이너에 전달할 환경 변수를 정의한다. 배열과 map 형식을 모두 지원하지만 값의 구조가 잘 보이는 map 형식이 읽기 편하다.

```yaml
services:
  api:
    environment:
      APP_ENV: development
      DEBUG: "true"
      DB_HOST: db
```

YAML이 `true`, `false`, `yes`, `no`를 boolean으로 해석할 수 있으므로 문자열로 전달하려면 따옴표를 사용한다.

민감한 값을 Compose 파일에 직접 기록하면 Git에 노출될 수 있다. 환경 변수, 별도의 비밀 관리 도구 또는 필요한 경우 Compose의 `secrets` 기능을 사용한다. `.env`는 변수 관리를 편하게 하지만 그 자체로 암호화된 비밀 저장소는 아니다.

### `command`

이미지에 정의된 기본 `CMD`를 덮어쓴다.

```yaml
services:
  api:
    image: example/api:1.0
    command: ["./server", "--port", "8080"]
```

실행 파일과 인자를 구분하기 쉬운 list 형식을 사용하면 셸의 공백 및 인용 처리에서 발생하는 혼동을 줄일 수 있다. 파이프나 변수 확장처럼 셸 기능이 필요하다면 셸을 명시한다.

```yaml
command: ["/bin/sh", "-c", "echo $${APP_ENV} && ./server"]
```

### `ports`

호스트 포트와 컨테이너 포트를 연결한다. 항목 이름은 `port`가 아니라 `ports`이다.

```yaml
services:
  web:
    ports:
      - "8080:80"
      - "127.0.0.1:8443:443"
```

```text
HOST_IP:HOST_PORT:CONTAINER_PORT
127.0.0.1:8443:443
```

첫 번째 예시는 모든 호스트 인터페이스의 8080 포트를 컨테이너의 80 포트에 연결한다. 두 번째 예시는 로컬 호스트에서만 접근할 수 있다. 포트 값은 YAML 숫자 해석 문제를 피하기 위해 문자열로 작성하는 편이 안전하다.

서비스 사이의 통신에는 호스트 포트가 아니라 컨테이너 포트와 서비스 이름을 사용한다.

```text
호스트 브라우저 → localhost:8080
다른 서비스     → web:80
```

### `depends_on`

서비스의 생성 및 종료 순서를 표현한다.

짧은 형식은 의존 서비스가 먼저 시작되도록 하지만 애플리케이션이 요청을 받을 준비가 끝날 때까지 기다리지는 않는다.

```yaml
services:
  api:
    depends_on:
      - db
```

준비 완료까지 기다려야 한다면 의존 서비스에 `healthcheck`를 정의하고 긴 형식을 사용한다.

```yaml
services:
  api:
    depends_on:
      db:
        condition: service_healthy

  db:
    image: postgres:18-alpine
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 10s
      timeout: 5s
      retries: 5
```

`depends_on`만으로 네트워크 연결 실패가 사라지는 것은 아니다. 애플리케이션도 일시적인 연결 실패에 대한 재시도 로직을 갖는 것이 좋다.

### `volumes`

서비스가 사용할 bind mount 또는 named volume을 컨테이너 경로에 연결한다.

```yaml
services:
  api:
    volumes:
      - ./src:/app/src:ro
      - app-data:/app/data

volumes:
  app-data:
```

- `./src:/app/src:ro`: 호스트 디렉터리를 읽기 전용으로 연결한 bind mount
- `app-data:/app/data`: Docker가 관리하는 named volume

### `networks`

서비스가 참여할 네트워크를 지정한다. 두 서비스가 서로 통신하려면 하나 이상의 네트워크를 공유해야 한다.

```yaml
services:
  api:
    networks:
      - frontend
      - backend

  db:
    networks:
      - backend

networks:
  frontend:
  backend:
```

이 구성에서 `api`는 두 네트워크에 모두 연결되지만 `db`는 `backend`에만 연결된다.

### `links`

`links`는 다른 서비스에 별칭을 부여하는 기능이다.

```yaml
services:
  web:
    links:
      - db:database
```

현재 Compose에서는 같은 네트워크의 서비스가 기본적으로 서비스 이름을 통해 서로를 찾으므로 일반적인 연결을 위해 `links`를 사용할 필요가 없다. 대부분은 공통 `networks`와 `depends_on`을 명시하는 편이 관계를 더 분명하게 표현한다.

### `restart`

컨테이너 프로세스가 종료되었을 때 Docker Engine이 적용할 재시작 정책이다.

```yaml
services:
  api:
    restart: unless-stopped
```

주요 값은 `no`, `always`, `on-failure`, `unless-stopped`이다. 재시작 정책은 오류의 원인을 해결하지 않으므로 로그와 상태 확인도 함께 필요하다.

### `healthcheck`

컨테이너 프로세스가 살아 있는지뿐 아니라 서비스가 정상적으로 응답할 준비가 되었는지 검사한다.

```yaml
services:
  web:
    image: nginx:alpine
    healthcheck:
      test: ["CMD", "wget", "-q", "--spider", "http://localhost/"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 10s
```

healthcheck 명령에 사용하는 프로그램은 컨테이너 이미지 안에 실제로 설치되어 있어야 한다.

### `extends`

다른 Compose 파일 또는 같은 파일의 서비스 설정을 가져와 확장한다.

```yaml
services:
  web:
    extends:
      file: compose.common.yaml
      service: web-base
    environment:
      APP_ENV: development
```

`extends`는 참조한 서비스가 의존하는 네트워크, 볼륨과 다른 서비스까지 자동으로 가져오지 않는다. 필요한 리소스는 최종 Compose 모델에 직접 선언해야 한다. 설정이 단순하다면 여러 `-f` 파일을 병합하거나 YAML anchor와 `x-` extension을 사용하는 방법도 고려할 수 있다.

## 네트워크 정의

별도 네트워크를 선언하지 않아도 Compose는 프로젝트 전용 `default` 네트워크를 자동으로 만든다.

```yaml
services:
  web:
    image: nginx:alpine
```

필요한 경우 최상위 `networks`에서 네트워크를 명시적으로 정의한다.

### `driver`

네트워크 생성에 사용할 드라이버를 지정한다.

```yaml
networks:
  backend:
    driver: bridge
```

일반적인 단일 Docker 호스트의 Compose 환경에서는 `bridge`가 기본값이다.

### `ipam`

IP 주소 범위와 gateway를 직접 지정한다.

```yaml
networks:
  backend:
    ipam:
      driver: default
      config:
        - subnet: 172.28.0.0/16
          gateway: 172.28.0.1
```

고정된 대역이 반드시 필요한 경우에만 사용한다. 기존 Docker 네트워크, 회사 VPN 또는 호스트 네트워크와 대역이 겹치면 통신 문제가 발생할 수 있다.

### `external`

Compose가 새로 만들지 않고 이미 존재하는 네트워크를 사용한다.

```yaml
networks:
  shared-network:
    external: true
    name: company-shared-network
```

external 네트워크가 존재하지 않으면 Compose는 오류를 반환한다. 이 네트워크의 생명주기는 현재 프로젝트 밖에서 관리되므로 `docker compose down`으로 제거되지 않는다.

## 볼륨 정의

최상위 `volumes`는 서비스가 사용할 named volume을 선언한다.

```yaml
services:
  db:
    image: postgres:18-alpine
    volumes:
      - db-data:/var/lib/postgresql/data

volumes:
  db-data:
```

Compose는 기본적으로 `<프로젝트 이름>_db-data` 형태의 실제 볼륨을 만든다.

### `driver`

볼륨을 생성할 드라이버를 지정한다.

```yaml
volumes:
  db-data:
    driver: local
```

`local`은 기본 드라이버이므로 보통 생략할 수 있다. NFS 같은 외부 스토리지를 사용하면 드라이버와 `driver_opts`를 환경에 맞게 설정한다.

### `external`

이미 만들어진 볼륨을 사용한다.

```yaml
volumes:
  db-data:
    external: true
    name: existing-postgres-data
```

Compose는 external volume을 생성하거나 `down --volumes`로 제거하지 않는다. 볼륨이 미리 존재하지 않으면 오류가 발생한다.

## YAML 파일 검증하기

Compose 파일을 실행하기 전에 `config`로 문법, 변수 치환과 파일 병합 결과를 확인한다.

```bash
docker compose config
```

출력 없이 유효성만 검사하려면 다음 명령을 사용한다.

```bash
docker compose config --quiet
```

특정 정보만 확인할 수도 있다.

```bash
docker compose config --services
docker compose config --images
docker compose config --networks
docker compose config --volumes
```

`config` 검증은 YAML과 Compose 모델이 유효한지 확인하지만, 이미지 내부에 명령이 존재하는지, 포트가 이미 사용 중인지, 애플리케이션이 DB에 연결되는지까지 보장하지는 않는다. 이러한 항목은 실제 실행 단계에서 로그와 상태를 확인해야 한다.

## 자주 발생하는 실수

- 최상위에 불필요한 `version`을 작성한다.
- `ports`를 `port`로 잘못 작성한다.
- 컨테이너에서 다른 서비스를 `localhost`로 접근한다.
- `depends_on`만으로 의존 서비스의 준비 완료까지 보장된다고 생각한다.
- 비밀번호를 Compose 파일에 직접 작성해 Git에 커밋한다.
- `docker compose down`이 named volume도 제거한다고 생각한다.
- 서비스 이름 기반 통신이 가능한데도 `links`를 필수로 사용한다.
- custom network와 external network의 IP 대역이 기존 네트워크와 충돌한다.
