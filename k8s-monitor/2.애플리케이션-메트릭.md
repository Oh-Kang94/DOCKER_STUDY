# 2. 애플리케이션 메트릭과 Exporter

## 공통으로 수집할 Metric

HTTP Service는 RED를 시작점으로 삼는다.

- Rate: 요청 수
- Errors: 실패 수·비율
- Duration: Latency 분포

Worker·Queue는 처리량, 실패, Queue Depth와 처리 지연을 추가한다. Business Metric은 주문·결제 같은 사용자 가치와 연결하되 개인 식별자를 Label로 넣지 않는다.

## Python·FastAPI

```python
from fastapi import FastAPI, Response
from prometheus_client import Counter, Histogram, generate_latest

app = FastAPI()
requests = Counter(
    \"shop_http_requests_total\",
    \"Total HTTP requests\",
    [\"method\", \"route\", \"status\"],
)
latency = Histogram(
    \"shop_http_request_duration_seconds\",
    \"HTTP request latency\",
    [\"route\"],
)

@app.get(\"/metrics\")
def metrics():
    return Response(generate_latest(), media_type=\"text/plain\")
```

실제 요청 Middleware에서 Counter와 Histogram을 기록한다. 여러 Worker Process를 쓰는 Python 배포는 prometheus-client Multiprocess Mode와 File Lifecycle을 별도로 구성하거나 OpenTelemetry Collector 경로를 검토한다.

## Go

```go
requests := prometheus.NewCounterVec(
	prometheus.CounterOpts{
		Name: \"shop_http_requests_total\",
		Help: \"Total HTTP requests\",
	},
	[]string{\"method\", \"route\", \"status\"},
)
prometheus.MustRegister(requests)
http.Handle(\"/metrics\", promhttp.Handler())
```

Default Registry에는 Go Runtime·Process Metric도 포함될 수 있다. Library Code에서 전역 MustRegister를 남용하지 않고 Registry 주입을 고려한다.

## Java

Spring Boot는 Micrometer와 Actuator Prometheus Registry를 사용한다.

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,prometheus
  endpoint:
    prometheus:
      access: read-only
```

기본 경로는 보통 `/actuator/prometheus`다. Actuator 전체를 외부에 노출하지 않고 별도 Management Port·인증·NetworkPolicy를 사용한다.

## JavaScript·TypeScript

```typescript
import client from \"prom-client\";

client.collectDefaultMetrics();
const requests = new client.Counter({
  name: \"shop_http_requests_total\",
  help: \"Total HTTP requests\",
  labelNames: [\"method\", \"route\", \"status\"],
});

app.get(\"/metrics\", async (_req, res) => {
  res.set(\"Content-Type\", client.register.contentType);
  res.end(await client.register.metrics());
});
```

Node.js Cluster Mode에서는 Worker별 Registry를 집계하는 방식을 Library Version에 맞춰 확인한다.

## Kubernetes Service

```yaml
apiVersion: v1
kind: Service
metadata:
  name: shop-metrics
  namespace: apps
  labels:
    app.kubernetes.io/name: shop
spec:
  selector:
    app.kubernetes.io/name: shop
  ports:
    - name: metrics
      port: 9090
      targetPort: metrics
```

ServiceMonitor는 숫자 Port보다 Service Port 이름 `metrics`를 참조한다.

## Metric Endpoint 확인

```bash
kubectl port-forward service/shop-metrics -n apps 9090:9090
curl --fail http://127.0.0.1:9090/metrics
```

Production Endpoint를 LoadBalancer로 공개하지 않는다.

## 유지보수 기준

- Route Label은 `/users/{id}` 같은 Template을 사용하고 실제 URL을 쓰지 않는다.
- Counter는 Process 재시작 시 0으로 돌아가므로 PromQL `rate()`를 사용한다.
- Latency 평균만 쓰지 말고 Histogram Bucket과 백분위를 설계한다.
- Metric Library와 Runtime Update 시 이름·Label 변경을 Contract Test한다.
- Metric 생성 자체의 CPU·Memory와 Cardinality 비용을 부하 시험한다.
