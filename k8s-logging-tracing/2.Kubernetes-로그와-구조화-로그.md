# 2. Kubernetes Log와 구조화 Log

## Container Log 흐름

Container Application은 기본적으로 Log를 `stdout`과 `stderr`에 기록한다. Container Runtime은 이를 CRI Log 형식의 Node 파일로 저장하고, kubelet이 Rotation을 관리하며, `kubectl logs`는 API Server와 kubelet을 통해 현재 파일을 읽는다.

```mermaid
flowchart LR
    app[Application<br/>stdout·stderr]
    runtime[Container Runtime<br/>CRI Logging]
    file[/var/log/pods<br/>/var/log/containers]
    kubelet[kubelet<br/>Rotation]
    api[Kubernetes API]
    cli[kubectl logs]
    agent[Node Log Agent]
    backend[Cluster Log Backend]

    app --> runtime --> file
    kubelet --> file
    file --> api --> cli
    file --> agent --> backend
```

Kubernetes는 Cluster 전체 Log를 장기간 저장하는 Backend를 기본 제공하지 않는다. Pod Eviction·Node 장애 뒤에도 조사하려면 Log의 저장 수명을 Pod와 Node에서 분리해야 한다.

## kubectl logs의 범위

```bash
kubectl logs pod/order-api-7f8d9c -n shop
kubectl logs pod/order-api-7f8d9c -n shop -c app
kubectl logs pod/order-api-7f8d9c -n shop -c app --previous
kubectl logs deployment/order-api -n shop --since=10m --tail=200
```

- 다중 Container Pod는 `-c`로 Container를 지정한다.
- `--previous`는 현재 Container의 바로 이전 Instance Log 확인에 사용한다.
- `kubectl logs`는 기본적으로 kubelet이 제공하는 최신 Log File 범위만 읽는다.
- Pod·Node가 사라진 뒤의 장기 검색과 여러 Pod 통합 검색은 Cluster Log Backend가 담당한다.

`kubectl logs` 성공은 중앙 Log 수집 성공을 의미하지 않는다. Node File은 정상이어도 Agent Output이나 Loki Ingestion이 실패할 수 있다.

## kubelet Log Rotation

kubelet은 `containerLogMaxSize`, `containerLogMaxFiles` 등으로 Container Log Rotation을 관리한다. 기본값을 그대로 사용하는지 Cluster 배포판의 Kubelet Configuration을 확인한다.

```yaml
containerLogMaxSize: 10Mi
containerLogMaxFiles: 5
containerLogMaxWorkers: 1
containerLogMonitorInterval: 10s
```

이 YAML은 Kubelet Configuration 일부이지 Pod Manifest가 아니다. Rotation을 크게 늘리면 Node Disk가 고갈될 수 있고, 너무 작게 설정하면 Agent 장애 중 보존할 수 있는 시간이 짧아진다.

## 수집 방식 비교

| 방식 | 장점 | 주의점 |
| --- | --- | --- |
| Node Agent DaemonSet | Application 변경 없이 모든 Pod Log 수집 | HostPath·RBAC·Node Resource 필요 |
| Streaming Sidecar | File Log를 stdout으로 변환 가능 | Pod마다 Resource·Storage 중복 |
| Sidecar Agent | Application별 특수 Parsing 가능 | 운영 복잡성과 비용 증가 |
| Application Direct Push | Context를 풍부하게 전달 가능 | Backend 장애가 Application에 전파될 위험 |

일반적인 신규 Application은 stdout·stderr에 기록하고 Node Agent가 수집하는 방식을 기본으로 한다. File만 지원하는 Legacy Application은 Shared Volume과 Streaming Sidecar를 제한적으로 사용한다.

## 구조화 JSON Log

한 줄에 하나의 JSON Object를 기록하면 Collector가 Message를 추측해 Parsing하는 비용과 오류가 줄어든다.

```json
{
  "timestamp": "2026-07-28T10:15:30.123Z",
  "severity": "ERROR",
  "service.name": "order-api",
  "deployment.environment.name": "prod",
  "event.name": "payment.authorization.failed",
  "message": "payment provider rejected request",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "http.request.method": "POST",
  "http.response.status_code": 502,
  "error.type": "PaymentRejected"
}
```

### 권장 필드

- Timestamp와 Severity
- 안정적인 `service.name`과 환경
- 사람이 읽을 `message`와 집계 가능한 `event.name`
- 현재 Trace Context의 `trace_id`·`span_id`
- 결과 상태와 Error Type
- 필요한 최소 Business Context

필드 이름은 OpenTelemetry Semantic Conventions와 팀 내부 Log Schema를 기준으로 관리한다. 같은 의미를 `status`, `statusCode`, `http_status`처럼 여러 이름으로 만들지 않는다.

## Multiline 문제

Stack Trace처럼 여러 줄인 Log는 CRI 단위와 Collector Parser에서 하나의 Event로 재조립해야 한다. 가장 안전한 방법은 Application이 Stack Trace를 JSON 문자열의 `exception.stacktrace` 한 필드로 기록하는 것이다.

```json
{"severity":"ERROR","message":"request failed","exception.stacktrace":"line 1\nline 2\nline 3"}
```

Collector의 Multiline 규칙에만 의존하면 Runtime 형식, 언어와 Version 변화로 Event가 잘못 합쳐질 수 있다. 최대 Line 크기와 Multiline Buffer 제한도 함께 둔다.

## 남기면 안 되는 데이터

- Password, Access Token, Session Cookie와 Authorization Header
- Private Key와 Connection String
- 주민등록번호·결제정보 같은 규제 대상 정보
- 전체 Request·Response Body의 무조건 기록
- User 입력을 검증 없이 그대로 기록한 값

민감정보는 Application에서 기록하지 않는 것이 가장 안전하다. Collector Redaction은 방어 계층이지 Application Logging Review를 대신하지 않는다. `trace_id`도 Loki Index Label로 만들면 Cardinality가 폭발하므로 Log Body나 Structured Metadata로 보관한다.

## Log Level과 비용

- `ERROR`: 처리가 실패했고 운영 판단이 필요한 Event
- `WARN`: 복구했지만 비정상 조건이 있었던 Event
- `INFO`: 주요 Business·Lifecycle Event
- `DEBUG`·`TRACE`: 제한된 기간과 대상에서만 활성화

Production 전체에서 Debug Log를 장기간 켜면 Storage 비용뿐 아니라 CPU, Network와 민감정보 노출 위험이 증가한다. Dynamic Level 변경에는 만료 시간과 Audit 기록을 둔다.

## System·Audit Log

Container Log 외에도 kubelet·Container Runtime의 journald, Control Plane Log와 Kubernetes Audit Log가 있다. Source, 권한, 보존 목적이 다르므로 Application Log와 같은 Pipeline에 무조건 합치지 않는다.

- System Log: Node와 Control Plane 장애 분석
- Audit Log: Kubernetes API 요청의 보안·규정 감사
- Application Log: Service 동작과 Business Event 분석

Audit Log에는 User·Resource 정보가 포함될 수 있으므로 별도 접근 권한, 장기 보존과 위변조 방지 정책을 검토한다.
