# 3. Fluent Bit Log 수집

## 역할과 배치 구조

Fluent Bit는 각 Node의 CRI Log File을 Tail하고, Kubernetes Metadata를 추가한 뒤 Loki로 전송하는 경량 Log Processor다. 모든 Workload Node의 Log를 읽어야 하므로 일반적으로 DaemonSet으로 배치한다.

```mermaid
flowchart TB
    subgraph node1[Node 1]
        p1[Pod A stdout]
        f1[/var/log/containers/*.log]
        a1[Fluent Bit]
        db1[Position DB·Buffer]
        p1 --> f1 --> a1
        a1 <--> db1
    end
    subgraph node2[Node 2]
        p2[Pod B stdout]
        f2[/var/log/containers/*.log]
        a2[Fluent Bit]
        db2[Position DB·Buffer]
        p2 --> f2 --> a2
        a2 <--> db2
    end
    a1 --> loki[Loki Gateway]
    a2 --> loki
```

신규 구성은 Grafana의 과거 Community Loki Plugin이 아니라 Fluent Bit에 포함된 공식 `loki` Output Plugin을 사용한다. Promtail은 Loki 3.7.3에서 제거되었으므로 새 설치의 기본 Agent로 선택하지 않는다.

## 설치 방식

Kubernetes에서는 공식 Fluent Helm Chart를 기준으로 Version을 고정해 관리하는 것이 편리하다.

```bash
helm repo add fluent https://fluent.github.io/helm-charts
helm repo update
helm search repo fluent/fluent-bit --versions

helm upgrade --install fluent-bit fluent/fluent-bit \
  --namespace observability \
  --create-namespace \
  --version <reviewed-chart-version> \
  --values values-fluent-bit.yaml
```

학습 환경에서도 설치 시점의 최신 Version을 무조건 자동 선택하지 않는다. Chart, Fluent Bit Image와 Loki 호환성을 검토한 뒤 Version을 Git에 기록한다.

## Pipeline Configuration

다음은 학습용 Fluent Bit YAML Configuration의 핵심이다. 실제 Helm Chart의 Values 구조와 Config Mount 방식은 선택한 Chart Version에서 확인한다.

```yaml
service:
  flush: 1
  log_level: info
  storage.path: /var/lib/fluent-bit/storage

pipeline:
  inputs:
    - name: tail
      tag: kube.*
      path: /var/log/containers/*.log
      multiline.parser: cri
      db: /var/lib/fluent-bit/tail.db
      mem_buf_limit: 50MB
      skip_long_lines: true
      storage.type: filesystem

  filters:
    - name: kubernetes
      match: kube.*
      kube_url: https://kubernetes.default.svc:443
      kube_ca_file: /var/run/secrets/kubernetes.io/serviceaccount/ca.crt
      kube_token_file: /var/run/secrets/kubernetes.io/serviceaccount/token
      merge_log: true
      merge_log_key: app
      keep_log: false
      labels: true
      annotations: false

  outputs:
    - name: loki
      match: kube.*
      host: loki-gateway.observability.svc
      port: 80
      labels: cluster=study,namespace=$kubernetes['namespace_name'],service_name=$app['service.name']
      structured_metadata: pod=$kubernetes['pod_name'],container=$kubernetes['container_name'],trace_id=$app['trace_id'],span_id=$app['span_id']
      line_format: json
      compress: gzip
      retry_limit: false
```

### Input

- `path`: Node의 Container Log Symlink를 Tail한다.
- `multiline.parser: cri`: CRI Partial Record와 Multiline을 처리한다.
- `db`: File별 읽은 Offset을 저장한다.
- `mem_buf_limit`: Output 장애 때 Memory가 무한히 늘지 않게 한다.
- `storage.type: filesystem`: Memory Queue를 넘은 Chunk를 Disk에 Buffering한다.

Position DB와 Buffer를 `emptyDir`에만 두면 Fluent Bit Pod 재시작 때 상태가 사라진다. HostPath나 유지 가능한 Node Storage를 사용하되 Disk Quota·권한·정리 정책을 둔다.

### Kubernetes Filter

Kubernetes Filter는 File Tag와 API를 사용해 Namespace, Pod, Container와 Label Metadata를 추가한다. 모든 Pod Label과 Annotation을 무조건 Loki Label로 보내지 않는다.

`merge_log`는 Application이 JSON 문자열을 출력했을 때 필드로 Parsing한다. JSON이 아닌 값은 원문을 유지하도록 실패 동작을 확인한다.

### Loki Output

- Label: `cluster`, `namespace`, `service_name`처럼 값의 범위가 작고 오래 유지되는 항목
- Structured Metadata: `pod`, `container`, `trace_id`, `span_id`처럼 Cardinality가 높은 조사 항목
- Log Body: Message, Stack Trace와 나머지 JSON Field

`auto_kubernetes_labels`는 편하지만 모든 Kubernetes Label을 Loki Stream Label로 만들어 Cardinality를 높일 수 있다. 명시적인 Allowlist를 기본으로 한다.

## DaemonSet Mount와 권한

핵심 Mount 구조는 다음과 같다.

```yaml
volumeMounts:
  - name: varlog
    mountPath: /var/log
    readOnly: true
  - name: state
    mountPath: /var/lib/fluent-bit

volumes:
  - name: varlog
    hostPath:
      path: /var/log
      type: Directory
  - name: state
    hostPath:
      path: /var/lib/fluent-bit
      type: DirectoryOrCreate
```

Log Directory는 읽기 전용으로 Mount하고 State Directory만 쓰기 가능하게 한다. Distribution에 따라 Container Log 실제 경로, SELinux·AppArmor와 Windows Node 경로가 다르므로 공식 Chart 값을 그대로 가정하지 않는다.

Kubernetes Metadata 조회용 ServiceAccount에는 필요한 Pod·Namespace 조회 권한만 부여한다. Secret 읽기 권한은 필요하지 않다.

## 확인 순서

```bash
kubectl get daemonset,pod -n observability -l app.kubernetes.io/name=fluent-bit
kubectl logs daemonset/fluent-bit -n observability --tail=200
kubectl port-forward service/loki-gateway -n observability 3100:80
curl http://127.0.0.1:3100/ready
```

Grafana Explore 또는 Loki API에서 최근 Log를 확인한다.

```bash
curl --get http://127.0.0.1:3100/loki/api/v1/query_range \
  --data-urlencode 'query={cluster="study"}' \
  --data-urlencode 'limit=20'
```

## Backpressure와 유실

Loki가 느리거나 Network가 끊기면 Fluent Bit는 Retry와 Buffer를 사용한다. `retry_limit: false`는 계속 재시도하지만 Disk가 가득 차면 결국 수집이 멈출 수 있다.

반드시 관찰할 항목은 다음과 같다.

- Input Record·Byte Rate
- Output Retry·Error·Dropped Record
- Memory와 Filesystem Buffer 사용량
- Tail File Rotation·Position DB Error
- Kubernetes Metadata API Error
- Fluent Bit Pod Restart와 Node Disk 사용량

무한 재시도는 무한 보존이 아니다. 최대 장애 시간을 정하고 그 시간 동안의 Log 양을 기준으로 Buffer를 산정한다.

## 유지보수 기준

- Fluent Bit·Chart·Loki Version 조합을 Upgrade Test한다.
- CRI와 Docker Parser를 Runtime에 맞게 선택한다.
- Parser 변경 전 원본 Sample Log로 회귀 Test한다.
- Agent 자신이 생성한 Log를 다시 수집해 Loop가 생기지 않게 한다.
- Backend Credential은 Secret으로 주입하고 TLS 검증을 끄지 않는다.
- 필터로 민감정보를 제거했는지 Sample을 실제 Query해 확인한다.
